# Feature Specification: Fix Image Content Path Validation

**Feature Branch**: `003-fix-image-content-path-validation`  
**Created**: 2026-04-23  
**Status**: Draft  
**Input**: User description: "Fix image retrieval tool content_path validation"

## Revised Root Cause (from bug_context.txt analysis)

The production error is **primarily a prompt/tool description issue**, not a validation logic bug:

1. The AI agent searched a **text-only index** (`index-and-vectorize`) that has no `content_path` field
2. Search results contained only `chunk_id`, `parent_id`, `chunk`, `title` — no image content
3. The AI agent **hallucinated** a blob URL by decoding the base64 `parent_id` field, producing a `.pdf` source document URL
4. The agent passed this PDF URL to `get_image_from_content_path`, which correctly rejected it
5. The tool description was too vague ("use content paths returned by semantic_search") — the agent interpreted this loosely

The fix addresses both the prompt issue (primary) and hardens the validation logic (secondary).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Retrieve Image via Valid Blob-Relative Content Path (Priority: P1)

An AI agent calls `semantic_search`, which returns search results containing image content. The agent extracts the `content_path` field from a result hit (e.g., `<container-name>/<path>/normalized_images_1.jpg`) and passes it to `get_image_from_content_path`. The tool validates the path and successfully downloads and returns the image.

**Why this priority**: This is the primary use case — the tool must accept the content_path values that actually come back from the Azure AI Search index for image results. Without this, the entire image retrieval feature is broken.

**Independent Test**: Call `get_image_from_content_path` with a blob-relative path like `my-container/documents/normalized_images_1.jpg` and verify the image is returned.

**Acceptance Scenarios**:

1. **Given** a content_path of `<container>/path/to/normalized_images_1.jpg` returned by semantic_search, **When** the agent passes it to `get_image_from_content_path`, **Then** the image is downloaded and returned as MCP Image content.
2. **Given** a content_path with URL-encoded characters (e.g., `container/011-WSH3001L%20%20Introduction%20to%20UAS%20(08%20May%2024)/normalized_images_1.jpg`), **When** passed to the tool, **Then** the path is decoded and the image is returned successfully.

---

### User Story 2 - Retrieve Image via Full Blob Storage URL (Priority: P1)

An AI agent receives a full blob storage URL as the `content_path` from a search result (e.g., `https://<account>.blob.core.windows.net/<container>/path/normalized_images_1.jpg`). The tool accepts this URL and downloads the image.

**Why this priority**: Some search index configurations return full blob URLs rather than relative paths. The tool must handle both formats.

**Independent Test**: Call `get_image_from_content_path` with a full blob storage URL pointing to a valid image blob and verify the image is returned.

**Acceptance Scenarios**:

1. **Given** a full blob URL like `https://account.blob.core.windows.net/container/path/normalized_images_1.jpg`, **When** passed to the tool, **Then** the image is downloaded and returned.
2. **Given** a full blob URL for Azure Government cloud (`.blob.core.usgovcloudapi.net`), **When** passed to the tool, **Then** the image is downloaded and returned.

---

### User Story 3 - Reject Clearly Non-Image Paths with Helpful Error (Priority: P2)

When an AI agent mistakenly passes a source document path (e.g., a `.pdf` URL) instead of an image content_path, the tool rejects it with a clear, actionable error message that helps the agent self-correct.

**Why this priority**: Good error messages prevent agents from retrying invalid calls and guide them toward the correct behavior. However, the rejection logic must not be so strict that it blocks valid image paths.

**Independent Test**: Call `get_image_from_content_path` with a PDF URL and verify a `ValueError` is raised with a descriptive message.

**Acceptance Scenarios**:

1. **Given** a content_path pointing to a `.pdf` document like `https://account.blob.core.windows.net/container/document.pdf`, **When** passed to the tool, **Then** a `ValueError` is raised with a message indicating the path does not appear to be an image.
2. **Given** a content_path with extension `.docx`, `.xlsx`, or `.pptx`, **When** passed to the tool, **Then** a `ValueError` is raised.
3. **Given** an empty or whitespace-only content_path, **When** passed to the tool, **Then** a `ValueError` is raised indicating the path cannot be empty.

---

### User Story 4 - Accept Content Paths Without File Extensions (Priority: P2)

Some content_paths from Azure AI Search may not have a recognizable file extension (e.g., encoded blob paths, paths with query parameters, or paths generated by the search indexer pipeline). The tool should attempt to download these rather than reject them outright.

**Why this priority**: The search index pipeline can produce content_paths in various formats. Being too strict about file extensions breaks valid use cases.

**Independent Test**: Call `get_image_from_content_path` with a content_path that lacks a file extension but points to a valid image blob, and verify the download is attempted.

**Acceptance Scenarios**:

1. **Given** a content_path like `container/path/to/normalized_images_1` (no extension), **When** passed to the tool, **Then** the tool attempts to download the image rather than rejecting it.
2. **Given** a content_path with query parameters like `container/path/image.jpg?sv=2021-06-08&st=...`, **When** passed to the tool, **Then** the tool extracts the path, recognizes the image extension, and downloads successfully.

---

### Edge Cases

- What happens when the content_path contains double URL encoding (e.g., `%2520` instead of `%20`)?
- How does the system handle a content_path that resolves to a blob that no longer exists?
- What happens when content_path contains special characters from non-English document titles?
- How does the system handle a content_path where the blob is an image but has a non-image extension (e.g., `.bin`)?
- What happens when the `normalized_images_` naming pattern changes in a future indexer pipeline version?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST accept blob-relative content_paths with recognized image extensions (`.jpg`, `.jpeg`, `.png`, `.gif`, `.webp`, `.bmp`, `.tif`, `.tiff`) and download the image.
- **FR-002**: The system MUST accept full blob storage URLs (both commercial and government cloud endpoints) with recognized image extensions and download the image.
- **FR-003**: The system MUST accept content_paths that contain URL-encoded characters and correctly decode them before validation and download.
- **FR-004**: The system MUST reject content_paths with extensions belonging to known non-image document formats (`.pdf`, `.docx`, `.xlsx`, `.pptx`, `.txt`, `.csv`, `.html`) with a descriptive `ValueError`.
- **FR-005**: The system MUST attempt to download content_paths that have no file extension rather than rejecting them, since the search indexer may produce extensionless paths for valid image content.
- **FR-006**: The system MUST reject empty or whitespace-only content_paths with a `ValueError`.
- **FR-007**: The error message for rejected paths MUST indicate what was wrong and guide the caller toward using the correct content_path from semantic_search results.
- **FR-008**: The internal `_download_blob_image` function MUST apply the same relaxed validation as the public tool, so that valid paths are not silently rejected and return `None`.

### Key Entities

- **content_path**: A string representing the location of image content in Azure Blob Storage. Can be a blob-relative path (e.g., `container/path/normalized_images_1.jpg`) or a full blob URL. Returned by `semantic_search` in the `content_path` field of search result hits.
- **Image**: An MCP Image content object returned by `get_image_from_content_path`, suitable for rendering by MCP clients.
- **Search Index**: The Azure AI Search index that stores document and image content, with a `content_path` field that references the blob storage location of extracted images.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All content_paths returned by semantic_search for image results are accepted by `get_image_from_content_path` without validation errors — 100% of valid image content_paths succeed.
- **SC-002**: Non-image document paths (PDF, DOCX, etc.) are still rejected with a clear error message — 100% of known document extensions are caught.
- **SC-003**: URL-encoded content_paths (including paths with spaces, parentheses, and special characters) are handled correctly — zero failures due to encoding issues.
- **SC-004**: Error messages for rejected paths are actionable — they identify why the path was rejected and what kind of path is expected.
- **SC-005**: The fix introduces no regression in existing image download functionality for paths that already work (blob-relative paths with image extensions).

## Assumptions

- The Azure AI Search index `content_path` field for image content typically follows the pattern `<container>/<path>/normalized_images_N.<ext>`, but other formats may exist depending on indexer pipeline configuration.
- The blob storage account and container are correctly configured via environment variables (`STORAGE_ACCOUNT_BLOB_ENDPOINT`, `STORAGE_ACCOUNT_CONTAINER_NAME`).
- The existing blob download logic (exact match + suffix fallback) works correctly once validation passes — only the validation gate is broken.
- The error in production logs (`ValueError: content_path '...pdf' does not look like an image path`) indicates the AI agent was passed a source document URL rather than the image content_path. The fix should both (a) handle valid image paths that were incorrectly rejected and (b) ensure error messages help the agent select the right field.
- The `_IMAGE_EXTENSIONS` set already contains the correct set of recognized image file extensions.
